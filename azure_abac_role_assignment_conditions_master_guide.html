Azure Role Assignment Conditions (Azure ABAC)

Mastering Attribute-Based Access Control: Supported storage services, condition syntax, boolean logic evaluation, and how to deconstruct exam traps.

🎯 30-Second Exam Cheat Sheet:
• What is ABAC: Adding fine-grained conditional filters to an existing RBAC role assignment.
• Supported Storage Services: Supported on Blob Storage (containers & blobs) and Queue Storage ONLY. (Never Files or Tables!).
• The Disjunction Pattern: (Action != write) OR (Constraint) means all reads are 100% permitted; the constraint only restricts write operations.
• Attribute Sources: Request (path, container name), Resource (Blob Index Tags), Principal (Entra ID Custom Security Attributes).

1. Why Does Azure ABAC Exist?

In traditional Azure RBAC, access is governed strictly by the Scope (Management Group, Subscription, Resource Group, Resource).

The Problem: Imagine a storage account containing 500 blob containers. If you want UserA to access only 20 specific containers, you would have to create 20 separate role assignments at each container level.

  • Azure subscriptions enforce a hard limit of 4,000 role assignments.
  • Managing hundreds of micro-assignments causes massive administrative overhead.

The ABAC Solution: Assign the role once at the Storage Account scope, and attach a Condition (e.g., @Request[container:name] == 'archive'). Access is evaluated dynamically at runtime.

2. Supported Services & Resource Actions

Azure Service Supports Role Conditions? Key Supported Actions
Azure Blob Storage ✅ YES Read Blob, Write Blob, Delete Blob, Delete Blob Version, Add Blob, Create Container
Azure Queue Storage ✅ YES Read Messages, Add Messages, Delete Messages, Update Messages
Azure Files ❌ NO Not supported. (Exam Distractor!)
Azure Tables ❌ NO Not supported. (Exam Distractor!)

3. Anatomy of a Condition Expression

An Azure ABAC condition consists of an action check combined with attribute predicates:

( @Request[Microsoft.Storage/storageAccounts/blobServices/containers/blobs:path] StringLike 'finance/*' ) AND ( @Resource[Microsoft.Storage/storageAccounts/blobServices/containers/blobs/tags:Project{$key$}] StringEquals 'Alpha' )

The Three Sources of Attributes:

  1. Request Attributes (@Request): Parameters passed in the current REST API call (e.g., target container name, blob path prefix).
  2. Resource Attributes (@Resource): Metadata stored on the target Azure resource, specifically Blob Index Tags (key-value pairs indexed on blobs).
  3. Principal Attributes (@Principal): Metadata stored on the user identity in Microsoft Entra ID, specifically Custom Security Attributes.

4. The Boolean Logic Engine: The "Action != Write" Trap

In Microsoft certification exams, the test-writers love to test your understanding of Boolean Disjunction (OR).

Consider this standard condition template:

RuleBeta = (Action is NOT a blob-write) OR (Blob path contains '2')
User requests READ on file1.dat │ Is the operation a write action? / \ YES NO / \ Clause 1 = FALSE Clause 1 = TRUE │ │ Must check Clause 2: Condition SATISFIED! Does path contain '2'? (TRUE or Anything = TRUE) / \ │ YES NO ▼ Allowed DENIED ACCESS GRANTED
Why is it written with an OR?
If the policy were written as Blob path contains '2' without the Action != write clause, the user would be blocked from reading any other files! Adding (Action != write) OR ensures that read operations are completely unrestricted, and the path constraint is only enforced when the user attempts a write operation.
